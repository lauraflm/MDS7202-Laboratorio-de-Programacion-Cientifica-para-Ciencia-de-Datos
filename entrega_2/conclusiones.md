# Conclusiones

La implementación del enfoque MLOps en este proyecto permite visualizar de manera práctica el como las herramientas de automatización, trazabilidad y despliegue mejoran tanto la calidad del trabajo como la velocidad de desarrollo. A lo largo del proceso se hizo evidente que la ejecución de un pipeline que se encuentre bien estructurado no solo facilita el entrenamiento y la evaluación del modelo, sino que también hace más trazable el seguimiento de cada paso, es ordenada y visual, y con eso más estable el funcionamiento.

El almacenamiento de distintos componentes en carpetas específicas, es decir, que contengan los modelos entrenados, métricas, predicciones semanales, dió lugar a un sistema en el que cada ejecución deja un registro. Esto permitió filtrar con facilidad, comparar métricas entre versiones y recuperar modelos sin necesidad de volver a entrenar. Además, tener las predicciones de cada semana almacenadas como archivos independientes facilita la posterior utilización con el sistema de recomendación.

Aunque en esta versión del proyecto no utilizamos MLflow, consideramos que sería una herramienta muy valiosa para incorporar en futuras iteraciones del pipeline. Hasta ahora, el seguimiento de modelos, métricas y artefactos se realizó de manera manual mediante archivos guardados en carpetas específicas dentro de Airflow. Esto funciona, pero no ofrece un historial estructurado ni una comparación fácil entre diferentes entrenamientos. MLflow permitiría registrar automáticamente cada ejecución del modelo, almacenar métricas, guardar versiones del pipeline, lo que facilitaría la reproducibilidad y el análisis de desempeño a lo largo del tiempo.

Además, MLflow aporta ventajas importantes para la gestión de un flujo MLOps más profesional, ya que, permite comparar modelos, facilita el versionado de datasets y modelos, y abre la posibilidad de hacer despliegues más formales. Integrarlo en la próxima entrega permitiría que nuestro pipeline deje de depender de archivos sueltos y pase a tener un sistema centralizado de tracking que mejora la trazabilidad, el monitoreo continuo y la colaboración. Por estas razones, aunque no lo usamos en esta entrega, sí es una herramienta que queremos incorporar para la entrega final.

Por otro lado, el uso de Airflow como herramienta permitió visualizar el pipeline, teniendo tareas secuenciales, ramas condicionales y logs detallados de cada etapa para visualizar el funcionamiento. Esta plataforma hizo posible detectar rápidamente errores, re-ejecutar partes específicas del pipeline y analizar cómo se comporta cuando se tienen nuevos datos. La lógica de detección de drift y el reentrenamiento automático hicieron que el flujo sea más efectivo y permiten que el sistema decida cuándo actualizar el modelo.

Una herramienta que se utilizó fue Gradio, especialmente cuando se hizo el despliegue del sistema de recomendación y del chatbot. Gradio permitió levantar un frontend que sea interactivo y fácil de utilizar en muy pocos pasos, sin necesidad de conocimientos avanzados de desarrollo web. Esto fue valioso porque en este contexto no se cuenta con todas las herramientas para profundizar con elementos más avanzados. Con Gradio, fue posible transformar funciones Python en interfaces de usuario totalmente utilizables en muy poco tiempo, lo que aceleró el proceso de validación del modelo.

Además, su integración con FastAPI y Docker facilitó la separación entre backend y frontend, permitiendo un flujo coherente donde la API sirve los datos y Gradio actúa como lo visible para el usuario. Esto aportó claridad a la arquitectura, y demostró lo útil que puede ser una herramienta como Gradio para proyectos que necesitan interfaces simples, rápidas de construir y accesibles, incluso cuando no hay experiencia previa desarrollando frontends. Por eso, para una primera versión es una herramienta ideal.

En una versión futura del pipeline, sería útil agregar más monitoreo automático tanto de los datos como del modelo. Actualmente se detecta drift con PSI, pero podrían incluirse otras validaciones como revisar valores fuera de rango, analizar la tasa de compras o cambios inesperados. Esto ayudaría a anticipar problemas y evitar que datos anómalos entren al sistema. También se cree que sería valioso incorporar un sistema como MLflow. Aunque hoy se guardan los modelos y las predicciones semanales, un versionado más formal permitiría comparar entrenamientos, guardar parámetros y entender mejor la evolución del modelo.

En cuanto al despliegue, se podría mejorar la automatización de la llegada de nuevos datos, en donde por ejemplo, se podría validar automáticamente si llegó un nuevo archivo transacciones_*.parquet y a través de esto, poder verificar el contenido. Esto haría el ingreso de los datos de manera más segura y menos manual (que puede ser afectado por errores). Así, se podría tener una actualización constante y se podría replicar el análisis con datos nuevos, lo cual es útil para problemas como este. 

Finalmente, sería interesante agregar métricas de uso en producción, como cuántos clientes reciben recomendaciones cada semana, cómo cambian las probabilidades promedio o si el modelo empieza a perder precisión con el tiempo. Esto permitiría activar reentrenamientos no solo por drift en las features, sino también por baja de rendimiento del modelo.

En sintesis, aunque el pipeline actual funciona bien, hay cosas que se podrían incorportar con el fin de hacerlo más automatizado, más monitoreado y más robusto frente a cambios futuros. Estos son pasos secuenciales que permiten que se eviten errores y que logran que cuando ingresan nuevos datos, el proceso no tenga que hacerse todo de nuevo, si no que se aplica de la misma forma y es más efectivo el proceso de análisis.
